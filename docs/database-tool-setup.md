# Database and MCP Tool Setup

This feature is separate from the existing warehouse onboarding and chat pipeline.
Open Data Sources, create a workspace, then select **Tool setup**. Each workspace
can hold multiple server connections and independently selected databases. Tables
and views can generate executable tools. Procedures and their parameters are shown
for review only: a procedure must not be executed merely because its name looks
read-only.

## Deployment

From `apps/bi-dashboard`, apply the additive **application database** migration:

```sh
node --env-file=.env.local scripts/migrate-tool-setup.mjs
```

Configure these server environment variables:

- `SOURCE_DATABASE_ALLOWED_HOSTS`: comma-separated permitted server hosts/IPs.
  If unset, existing `WORKSPACE_ALLOWED_HOSTS`, or configured SQL Server/PostgreSQL
  hosts and localhost, are used. This is not a browser-editable allowlist.
- `TOOL_GENERATION_MODEL`: the advanced GPT model available to your OpenAI account.
  Defaults to `gpt-6-astra`, independently of the existing chat model. Account access
  must be verified; generation errors do not fall back silently to a weaker model.
  [Official model capabilities](https://developers.openai.com/api/docs/models/gpt-6-astra)
  confirm support for structured outputs and Chat Completions.
- `OPENAI_API_KEY`: existing application OpenAI credential; never entered into or
  returned from the setup UI.
- `WORKSPACE_SECRETS_KEY`: existing 32-byte encryption key.

Restart the application after changing configuration.

## Workflow

1. Connect using database type, host, port, credentials, initial database, and TLS.
2. List databases or enter a database name if catalog listing is restricted.
3. Discover each database separately. No copying, seeding, ETL, or source DDL runs.
4. Select actual tables/views and columns. Review verified foreign keys.
5. Approve sending selected metadata (not rows/passwords) to OpenAI and generate
   a small batch of structured tool suggestions. Repeat for other selections.
6. Review or edit columns, metrics, filters, and relationships using the form,
   test with real parameter values, and approve.
   Tests return at most 50 preview rows; this is not a full saved report export.
7. Approved tools become available from the workspace's authenticated MCP endpoint:
   `/api/workspaces/<workspace-id>/tools/mcp`.

The endpoint uses MCP Streamable HTTP in stateless JSON mode. It currently requires
the application's signed-in owner session, not an external bearer token. Tool names
are namespaced by database-source ID. No generated tools are loaded into the existing
chat yet; connecting them to a new chat workspace is a separate integration step.

## Safety and Limits

Source queries are generated by a restricted SELECT compiler. The model cannot
supply SQL. Filter values are bound parameters; identifiers must match discovered
objects. Joins require verified unique targets to avoid multiplication of records.
PostgreSQL/MySQL queries use read-only transactions; SQL Server uses fixed metadata
SELECTs and the SELECT compiler. Use SELECT-only source credentials as defense in
depth. No stored procedure calls, inserts, updates, deletes, or object creation occur.

Test success validates the query/parameters tested, not every possible business
question or parameter value. Preview limits do not prove billion-row performance.
Grouped aggregates compute in the source DB and may time out on expensive scans;
the returned groups are bounded and are never labelled the whole population.

Changed database metadata invalidates approval on rediscovery. Every execution and
approval also checks current metadata. Editing a draft clears its previous test;
approved definitions are copied under a new name rather than overwritten. Credentials
are encrypted in the app DB. Test result rows are not persisted. The app DB stores
connections, discovered catalogs, tool definitions, version counters, and approval/test
state. Tool-definition revisions and test-run outcomes are retained without result
rows or parameter values. Removing a tool explicitly deletes its history too.

## Tests

```sh
node --test lib/tool-setup/model.test.mjs lib/tool-setup/mcp.test.mjs
npx tsc --noEmit
```

Unit tests use in-memory metadata, never synthetic source tables or inserted records.
The optional `scripts/check-tool-setup-source.mjs` check loads the existing warehouse
SQL Server configuration and exercises discovery and two-row previews against the
real billing/ticketing databases. It does not persist data or make AI calls. The
SQL Server check reuses the existing connection's self-signed certificate setting;
the new UI requires explicitly opting into that setting when needed.
